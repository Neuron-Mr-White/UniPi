# Simple mode: remove extra blank lines below "Memory recall" badge and below "─ summary ─" divider

## Spec: does a blank row precede each text chunk? (full audit)

Every "text chunk" a simple-mode transcript can show, and what pi/unipi puts **before** it:

**A. Chat-level chunks** (direct children of `chatContainer`, spacing comes from pi):

| Chunk | Blank before? | Where it comes from |
|---|---|---|
| User message text | **1** (+1 inside its Box) | pi `addMessageToChat` adds `Spacer(1)`; the Box itself has `paddingY=1` (bg-colored, pi design) |
| Skill-invocation block | **1** | same chat-level `Spacer(1)` |
| Custom message badge (`▌ Memory recall …`) | **1** | pi `CustomMessageComponent` constructor adds `Spacer(1)` internally — pi-owned, not ours |
| Custom entry card (`▌ Memory palace …`) | **1** | pi `CustomEntryComponent` adds `Spacer(1)` |
| Assistant message | 0 at chat level — its blank lives **inside** (see B) | — |
| Tool group (`└ •` rows) | **1** | pi `ToolExecutionComponent.render` pushes `""` before non-empty self-rendered output; in simple mode only each group's last member paints → exactly one blank per group (designed separator) |
| Compaction / branch summary | **1** | chat-level `Spacer(1)` |
| Status / cache-miss / error notices | **1** | `Spacer(1)` + `Text` |

**B. Chunks inside one assistant message** (children of `contentContainer`):

| Chunk | Blank before? | Where it comes from |
|---|---|---|
| **First** text chunk of the message | **1 — the bug** | pi's `updateContent` inserts `Spacer(1)` as child #0 whenever the message has *any* visible content (non-empty thinking counts too). `stripBlankRuns` never removes it — it only drops blank hidden-thinking `MouseRegion`s and the spacer *after* each |
| Later text chunks in the same message (`text, toolCall, text`) | **0** | sibling `Markdown`s — no spacer between them (tool calls render as separate chat-level components *below* the whole message block, not between the text chunks) |
| Text after a hidden-thinking run | **0** | pi adds `Spacer(1)` (`hasVisibleContentAfter`), but `stripBlankRuns` removes it with the region — already handled |
| Hidden-thinking label row itself | **0** | escapes-only `Text` renders a full blank row — removed by `stripBlankRuns` — already handled |
| Error/abort/length line inside a message | **1** | pi `Spacer(1)` before the error `Text` (rare; pi design) |

**C. Chunks inside the reply panel** (`patchAssistantRender` painted array):

| Row | Blank? | Where it comes from |
|---|---|---|
| Above `─── summary ───` rule | **1** | designed breathing `""` |
| **Below** `─── summary ───` rule | **1 painted black — the bug** | `lines[0]` is pi's leading `Spacer(1)` from B, painted onto the panel bg before the reply text |
| Between text lines | content | Markdown's own inter-block `""` (only emitted when another token follows — never trailing; source is `text.trim()`) |
| Bottom pad + closing rule | **1** | designed pad |

**Answer:** pi's convention is "one spacer row before every chunk" — except assistant messages, which carry their spacer internally at `contentContainer` index 0, and later text chunks within one message, which are already flush. `stripBlankRuns` neutralized the thinking-related rows but left the leading `Spacer(1)`, which surfaces as **(1)** the painted blank under the `─ summary ─` divider and **(2)** the stray blank below the `Memory recall` badge whenever the next block is assistant text (and likewise above every mid-turn `● text`).

## Summary

- The two gaps the user spotted share one root cause: pi's leading `Spacer(1)` inside `AssistantMessageComponent.contentContainer` is never removed in simple mode.
- Gotcha for the fix: pi prepends `\x1b]133;A\x07` (OSC-133 zone start) to `lines[0]` of no-tool-call assistant messages (user messages too), so an SGR-only blank check misses it. Blank detection must strip OSC sequences, and zone markers must be carried onto surviving edge lines.
- Scope is safe: `patchAssistantRender` is installed only via `installSimpleGroupEvents` → `installReplyBackground`, which `packages/unipi/index.ts` runs only when `render.style === "simple"`. `regular`/`advanced` unaffected.
- One designed separator row remains below the badge in the tool-group and reply-panel cases (pi's `""` group prefix / the breathing row before the rule) — kept deliberately; zero-gap there would be a separate decision.

## Steps

1. **`packages/utility/src/render/reply-bg.ts`** — add two helpers and wire them into the patched render:
   - `isBlankRendered(line)`: strip OSC sequences (`\x1b]…\x07` and `\x1b]…\x1b\\`, covers `\x1b]133;[ABC]\x07`) **and** SGR (`\x1b[…m`), then `trim() === ""`.
   - `trimEdgeBlankLines(lines)`: drop leading and trailing rendered-blank lines. If a dropped edge line carried OSC-133 markers, reattach them to the first/last surviving line so terminal prompt-zone semantics survive.
   - In the wrapped `render()`: `const lines = trimEdgeBlankLines(original.call(this, width))`, placed before the `hasToolCalls || isStreaming || lines.length === 0` early return. This fixes both reported spots in one path — mid-turn text loses its stray blank (below-badge case) and the reply panel loses the painted blank under the divider.
   - Keep unchanged: `""` breathing row above the top rule, bottom `paintLine("", …)` pad, `isBlankStep`, `stripBlankRuns`, pi's `""` before tool groups, and all other pi chat-level spacers (user/custom/notice) — single designed separators.
2. **`packages/utility/tests/reply-bg.test.ts`** — update and extend:
   - Last test currently asserts `["", " hi"]` for children `[Spacer, hiddenRegion, Spacer, text]` — that leading `""` is exactly the bug; expected becomes `[" hi"]`.
   - New: reply panel — original render returns `["", "hello"]` → painted output puts `"hello"` directly under the labelled rule (no painted blank between rule and text).
   - New: leading blank carrying `\x1b]133;A\x07` is dropped and the marker moves onto the first surviving line.
   - New: all-blank render output → `[]`.
   - New: `hasToolCalls` mid-turn message also loses its leading blank row (flush `● text` under tool rows).

## Risks

- The prototype patch applies to **every** assistant component in simple mode — the leading blank disappears everywhere (the intended "compact" outcome); other render styles untouched.
- OSC-133 markers must be carried onto surviving edge lines or zone-aware terminals lose prompt-zone navigation.
- A single designed separator still shows below the badge in the tool-group and reply-panel cases. If zero gap is wanted there too, that's a separate follow-up — deliberately not in this change.
- `trimEdgeBlankLines` on all-blank output returns `[]`, matching existing `isBlankStep` behavior — no regression.
- Trimming operates on rendered lines only (no tree mutation), so it composes cleanly with the existing `stripBlankRuns` child-removal.
